# Fleet recall bridge (design, not built)

nvoy PR 333 added `may_recall` and the broker-side `recall` service. On nvoy-fleet the store is remote: herd-cloud's
Hive memory, reached as `hive-memory-gw@herd-cloud` over SSH with a per-agent read key. Murphy's pre-grant read
(12 Nov) found the gap. A `may_recall.read.command` runs inside the recall container, which has no SSH client and,
by design, no key. This note proposes the bridge. James's grants for GrokDoggyDog wait until it is built and reviewed.

## Shape

- **Host units, per instance, generated by the installer:** a socket unit `nvoy-recall-gw-<id>.socket`
  (`ListenStream=/run/nvoy-recall-gw/<id>/socket`, `Accept=yes`, `MaxConnections=4` (recall's in-flight limit),
  `SocketUser` = that instance's broker host user, `SocketMode=0660`, group = a **dedicated** group, `nvoy-recall-<id>`,
  whose only member is the recall container's uid; not the broker-adapter group, which other roles share). With
  `Accept=yes`, systemd starts one instance of a **template** per connection, so each instance gets its own template,
  `nvoy-recall-gw-<id>@.service`. The instance id lives in the unit *name*, and the per-connection instance string is
  systemd's connection id. So `User=`, the key path `/etc/nvoy/recall-keys/<id>` and the reader are fixed by the
  generated file, never derived from the connection (Murphy, PR 382 read). The template sets `StandardInput=socket`,
  `StandardOutput=socket` (SSH speaks over the accepted connection) and `StandardError=journal` (errors stay in the
  log, never in the pipe). It runs, as the broker host user, one fully pinned command and nothing else: `ssh -F /dev/null -i <key> -o IdentitiesOnly=yes -o IdentityAgent=none
  -o BatchMode=yes -o StrictHostKeyChecking=yes -o UserKnownHostsFile=<pinned> -o ClearAllForwardings=yes -o
  ConnectTimeout=10 -T hive-memory-gw@herd-cloud`. The gateway's forced command chooses the reader, and the client
  sends no arguments. A changed host key fails closed: the connection is refused and the error is logged, with no
  retry. The template sets `RuntimeMaxSec=25`, so a hung SSH can't pile up, plus `NoNewPrivileges=yes`,
  `ProtectSystem=strict`, `PrivateTmp=yes` and `ProtectHome=read-only`, and logs one line per connection with no
  request content.
- **The socket is a raw pipe.** The forwarder's two-tool allowlist runs inside recall, so a compromised recall could
  write any bytes to the socket. The gateway's forced command must itself refuse everything except a read-only
  wake or query for its bound reader, with no write method and no other reader. That is herd-cloud's existing
  reader gateway contract, which this PR does not prove: it is a live gate; the live gates below test it directly, not only through the forwarder (GrokDoggyDog,
  PR 382 read).
- **Key:** `/etc/nvoy/recall-keys/<id>` (mode 0600, owner the broker host user), on nvoy-fleet only. It is never
  mounted into any container. Making it, and authorizing its public half on herd-cloud's gateway as reader `<id>`,
  is the operator's step. The authorization is James's grant.
- **Container side:** the manifest uses `may_recall: { read: { socket: "/run/nvoy-recall-gw/socket" } }`. Compose
  bind-mounts only the instance's socket directory into `recall`, never into door, adapter or worker, with host-path
  creation off (`bind.create_host_path: false`), so a missing unit fails the start rather than Docker making an empty
  root-owned directory. Recall runs as a member of `nvoy-recall-<id>`, and its start is ordered after the socket unit.
  The rendered `recall` service sets `network_mode: none`. Compose otherwise attaches it to the default network, and
  that is the only way to make 'no network route' true (Murphy).
  `recall` keeps its current limits: two tools, 20 s, fail closed, 4 in flight, 1 MiB lines.
- **No new capability in the container:** no SSH binary is needed, there is no key path, and there is no network
  route. The socket is the only way out.

## Tests (to build)

- Render: `recall` gets the socket mount only when `may_recall.read.socket` is set. No other service gets it, and no
  service mounts `/etc/nvoy/recall-keys`.
- Forwarder against a fake socket gateway: wake and query pass through, while claim, submit and anything else are
  refused before any connection.
- Unit files: `ExecStart` is the fixed, pinned ssh line, with no client-supplied argument. The socket is 0660 with
  the dedicated group, `MaxConnections=4`, `RuntimeMaxSec` and the hardening keys present.
- Logging: drive one wake and one query through the unit with a marker string in the request, and check that the
  journal line carries the connection only (time, instance, exit status), never the marker or any request bytes.
- Render: `recall` has `network_mode: none` and no `networks` key; door, adapter and worker are unchanged.
- Socket activation round trip, for two distinct ids on one host: each socket reaches only its own template's
  instance, which runs as that id's user with that id's key path, and the bytes written come back over the same
  connection; stderr goes to the journal, not the socket.
- Compose: the socket bind uses `create_host_path: false`, recall has the dedicated group, and no other service has it.

## Done when (Murphy's live gates)

On nvoy-fleet:
- the key path and permissions are verified;
- the door, adapter and recall containers cannot read the key;
- the installed forced command and reader mapping, including any earlier reader key, are verified;
- the deployed SHA and socket permissions are verified;
- wake and query work live;
- a write or an arbitrary method is refused without contacting the store, both through the forwarder and as raw
  bytes sent straight to the socket (the gateway's own refusal);
- an outside-room read and a cross-instance read are both refused;
- the adapter and door containers cannot connect to the socket;
- the recall container has no network attachment (`docker inspect`: network mode none, no interfaces but lo);
- revoking the key's authorization on herd-cloud stops recall at once;
- no other key is authorized for this reader name, and this key is not shared with another instance.
